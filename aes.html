AES-128 from FIPS 197

An AES-128 implementation in C, written from the NIST standard. The S-box is derived from arithmetic in GF(28) instead of being copied as a table, and the field multiply and S-box run in constant time. The cipher itself is still in progress; this page covers what is done and how it was checked.

Arithmetic in GF(28)

AES treats each byte as a polynomial over GF(2) of degree below 8, reduced modulo the AES polynomial x8 + x4 + x3 + x + 1 (0x11b). Addition is XOR. Multiplying by x, called xtime, is a left shift; if the high bit was set before the shift, the result is reduced by XORing 0x1b. A general product a · b is the XOR of a · xi over the bits bi that are set, so gmul is eight rounds of "conditionally add a, then double a".

The S-box is defined by that field: take the multiplicative inverse of the byte (with 0 mapped to 0), then apply a fixed affine transform over GF(2). Instead of hardcoding the 256-byte table, the code computes it: 

static uint8_t affine_transform(uint8_t b){
    return (uint8_t) (b ^ rotl8(b, 1) ^ rotl8(b, 2)
    ^ rotl8(b, 3) ^ rotl8(b, 4) ^ 0x63);
}

The derived table matches FIPS 197 Figure 7. The first row, which the tests check byte for byte: 

63 7c 77 7b f2 6b 6f c5 30 01 67 2b fe d7 ab 76

Why table lookups leak timing

The usual way to implement SubBytes is sbox[b]. That is a memory load whose address depends on b, and in AES b depends on the key: in the first round the S-box input is a plaintext byte XORed with a key byte.

Memory is cached in lines, commonly 64 bytes, so a 256-byte table spans four lines. A load from a line that is already cached is fast; one that is not is slow. Which lines an encryption touches, and so how long it takes, therefore depends on the key. An attacker who can time many encryptions of known plaintexts, or who shares a cache with the victim and probes which lines were evicted, can work back to key bits. Bernstein (2005) recovered a full AES key this way from the timing of a server using table-based AES.

Branches leak the same way. if (b & 0x80) runs a different instruction sequence depending on a secret bit, which changes the running time and the state of the branch predictor.

So the rule for the code the cipher calls is: no branch and no memory address may depend on secret data. Loop counts are fine as long as they are fixed.

Replacing branches with masks

The reference xtime uses a conditional:

uint8_t refxtime(uint8_t b){
    uint8_t shifted = (uint8_t)(b << 1);
    uint8_t reduced = (uint8_t)((b & 0x80) ? 0x1b : 0x00);
    return (uint8_t)(shifted ^ reduced);
}

The constant-time version builds a mask from the high bit instead:

uint8_t xtime(uint8_t b){
    uint8_t shifted = (uint8_t)(b << 1);
    uint8_t reduced = (uint8_t)((-(b >> 7 & 1)));
    uint8_t masked = (uint8_t)((reduced & 0x1b));
    return (uint8_t)(shifted ^ masked);
}

b >> 7 & 1 is 0 or 1. In two's complement, negating 1 gives all ones, so truncated to a byte -(1) is 0xFF and -(0) is 0x00. ANDing that mask with 0x1b either keeps the reduction constant or zeroes it, and both cases execute the same instructions.

gcc at -O2 compiles it to straight-line code with no jumps:

gmul uses the same trick for "add a if this bit of b is set":

uint8_t gmul(uint8_t a, uint8_t b){
    int i;
    uint8_t result = 0x00;
    for (i = 0; i < 8; i++){
        uint8_t mask =(-(b & 1));
        result ^= (a & mask);
        b >>= 1;
        a = xtime(a);
    }
    return result;
}

The loop always runs eight times, so its only branch is the counter, which does not depend on a or b.

The inverse without a table: x254

Masks remove the branches, but the S-box still needs a multiplicative inverse, and a lookup into an inverse table would put a secret-dependent address back. The field structure gives a way around it. The nonzero elements of GF(28) form a group of order 255, so b255 = 1 for every nonzero b, and therefore b254 = b−1. For b = 0, 0254 = 0, which is exactly the convention AES uses, so zero needs no special case (a special case would itself be a branch). 

static uint8_t compb254(uint8_t b){
    int i;
    const uint8_t b1 = b; // OK: the original b, copied once.
    for(i = 0; i<253; i++){
        b = gmul(b, b1); // OK: exponent goes up by 1 each pass, b^1 -> b^254.
    }
    return b;
}

static uint8_t ntablesbox(uint8_t b){
    uint8_t b254 = compb254(b);
    uint8_t affine = affine_transform(b254);
    return affine;
}

Every input takes the same 253 multiplications, each a fixed eight-iteration loop, followed by the affine transform. The inverse S-box runs the steps backwards: undo the affine transform, then raise to the 254th power. 

static uint8_t invaffine(uint8_t x){
    x = rotl8(x,1) ^ rotl8(x,3) ^ rotl8(x,6) ^ 0x05;
    return x;
}
static uint8_t invsbox(uint8_t b){
    uint8_t unaff = invaffine(b);
    uint8_t inverse = compb254(unaff);
    return inverse;
}

The cost is speed. A table lookup is a single load; this is hundreds of field multiplications per byte. The straight loop is the simplest constant-time route to b254, not the fastest; square-and-multiply would reach it in far fewer multiplications.

The original branching and table-based versions (refxtime, refgmul, refsub_byte, refinv_sub_byte) are kept in the file only as the known-good answers the tests compare against.

How it was checked

Exhaustive comparison with the reference. A byte-sized domain is small enough to test completely. The constant-time functions are compared with the reference versions on all 256 inputs, and gmul on all 65,536 input pairs (tests/test_aes.c):

Known answers from the standard. The tests also check the FIPS 197 multiplication and xtime examples (for instance gmul(0x57, 0x83) == 0xc1), row 0 of Figure 7, sbox[0x53] == 0xed, that the S-box is a bijection, and that the inverse S-box undoes it on every byte.

Sanitizers and strict warnings. make test builds the harness with: 

CFLAGS = -std=c17 -O1 -Wall -Wextra -Wpedantic -Werror
SANITIZE = -fsanitize=address,undefined

Reading the assembly. A C compiler is free to turn mask arithmetic back into a branch, so the source alone proves nothing. The generated assembly was inspected at gcc -O0 and -O2: the only branches left in these functions are the fixed loop counters, and the only indexed loads are in the table-building and reference code used by the tests.

Limits. Inspecting one compiler's output at two optimization levels is evidence for that build, not a guarantee for every compiler or CPU. A statistical timing test has not been run yet, and the constant-time property has only been checked for the field arithmetic and S-box layer, not a full cipher.
